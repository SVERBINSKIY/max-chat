# Telegram Chat

Тестовое задание на позицию Frontend-разработчик (React): веб-интерфейс для отправки и получения текстовых сообщений через [GREEN-API](https://green-api.com/max). Внешний вид сделан по образцу [web.max.ru](https://web.max.ru/).

Проверялось на инстансе Telegram. Методы и формат уведомлений GREEN-API у MAX и Telegram одинаковые, поэтому с MAX приложение должно работать без изменений.

**Стек:** React 18, TypeScript, Vite, CSS Modules, Vitest + Testing Library. Runtime-зависимостей кроме React нет.

## Запуск

Нужен Node.js 18+.

```bash
npm install
npm run dev        # http://localhost:5173
```

| Команда             | Что делает                         |
| ------------------- | ---------------------------------- |
| `npm run build`     | проверка типов и production-сборка |
| `npm run preview`   | локальный просмотр сборки          |
| `npm test`          | тесты (Vitest)                     |
| `npm run lint`      | ESLint                             |
| `npm run typecheck` | `tsc --noEmit`                     |
| `npm run format`    | Prettier                           |

Те же проверки запускаются в CI (`.github/workflows/ci.yml`).

## Подготовка GREEN-API

1. Создайте инстанс в [личном кабинете](https://console.green-api.com) и авторизуйте его (QR-код).
2. В настройках, в блоке «Уведомления», включите **«Получать уведомления о входящих сообщениях и файлах»**. По умолчанию она выключена, и тогда ответы собеседника в очередь не попадают. Настройка применяется в течение нескольких минут. Если она выключена, приложение покажет предупреждение.
3. Поле `webhookUrl` должно быть пустым, иначе `ReceiveNotification` не работает.
4. Откройте приложение и войдите по `idInstance` и `apiTokenInstance`. Поле `apiUrl` (раздел «Дополнительно») нужно, только если хост в кабинете отличается от `https://api.green-api.com`.

## Сценарий

1. Вход по `idInstance` и `apiTokenInstance`. Данные проверяются методом `GetStateInstance`.
2. «+» → номер телефона получателя → чат создан.
3. Текст → Enter (Shift+Enter переносит строку) → сообщение уходит методом [`SendMessage`](https://green-api.com/v3/docs/api/sending/SendMessage/).
4. Ответ получателя появляется в чате: приложение получает его через [HTTP API](https://green-api.com/v3/docs/api/receiving/technology-http-api/).

## Устройство

```
src/
  api/            клиент GREEN-API, ошибки, разбор уведомлений (без React)
  features/
    auth/         хранение сессии
    chats/        состояние чатов и хуки получения/отправки сообщений
  components/     интерфейс
  lib/            мелкие утилиты (телефоны, время, storage)
```

Основные решения:

- **Состояние чатов — чистый редьюсер** (`chatsReducer.ts`). Вся логика (сопоставление входящих с чатами, дедупликация, счётчики) собрана в одном месте и покрыта тестами. Время и id приходят в экшенах, поэтому редьюсер детерминирован и безопасен в StrictMode.
- **Получение сообщений** (`useNotificationPolling`): цикл `ReceiveNotification → обработка → DeleteNotification`. Запрос отменяется через `AbortController` при размонтировании, при ошибках повтор идёт с нарастающей паузой (от 1 до 30 секунд). Обработчик сообщений хранится в ref, поэтому смена колбэка не перезапускает опрос.
- **Сопоставление ответа с чатом.** При создании чата вызывается `CheckAccount`, он возвращает `chatId` собеседника, с которым приходят входящие. Если проверка недоступна, сообщение уходит на `номер@c.us`, а ответ ищется по `senderPhoneNumber`. Это нужно, потому что в Telegram и MAX входящие приходят с числовым идентификатором, а номер телефона в уведомлении может отсутствовать.
- **Идемпотентность.** Если подтверждение (`DeleteNotification`) не дошло, GREEN-API пришлёт уведомление повторно. Дубли отсекаются по `idMessage`.
- **Разбор уведомлений** — без приведения типов: тело уведомления приходит как `unknown` и проходит через type guards (`api/notifications.ts`). Поддерживаются `textMessage` и `extendedTextMessage`, остальное по заданию игнорируется.
- **Ошибки.** Клиент превращает коды ответа в понятные сообщения (неверный токен, лимит тарифа Developer, лишний `webhookUrl`). Неудачную отправку можно повторить.
- **Хранение.** История чатов лежит в `localStorage` (по `idInstance`). Токен сохраняется в `localStorage` при включённом «Запомнить на этом устройстве», иначе только в `sessionStorage`. Бэкенда нет, поэтому токен остаётся в браузере пользователя.
- **Доступность.** Семантическая разметка (кнопки, `role="log"` для переписки, подписи у полей и иконок), видимый фокус, поддержка `prefers-reduced-motion` и тёмной темы.
- **Адаптивность.** На узких экранах список чатов и переписка открываются по очереди.

## Ограничения и что можно улучшить

- На тарифе Developer доступно только 3 чата в месяц.
- История не загружается с сервера (по заданию нужны только отправка и получение), показывается то, что было в этом браузере.
- Опрос идёт, пока открыта вкладка. При нескольких вкладках с одним инстансом уведомления между ними делятся: очередь у GREEN-API одна. Для продакшена получение стоило бы вынести на бэкенд (webhook + WebSocket/SSE).
- Только текстовые сообщения, без вложений, групп и статусов доставки.
